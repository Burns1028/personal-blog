# 《云图回忆录》重写设计

## 目标

把用户提供的口述长稿深度重写为一篇可直接阅读的个人回忆录。文章仍按“进入云图—实习—转正—正式工作—AI 时代的判断—离开云图”的时间顺序展开，不把它改造成脱离经历的技术观点合集。

深改只改变语言、段落组织、详略和衔接，不改变事件、人物关系、项目结论与作者判断。不补写用户没有提供的会议、对白、绩效结果、心理活动或项目细节。

## 写作模式

经验驱动。文章靠四年里真实发生的项目和选择成立：迁移老服务、商品竞争分析、OLAP 引擎迁移、转正答辩、实体切词、Multi-Agent 系统、跨角色协作，以及最终转去 Seed Infra 团队。

核心新增判断不是“我在云图成长了”，而是：四年里看似分散的经历，一直在校正同一种研发观——把复杂问题接住，在局部效果、系统代价和人的协作之间作出可靠判断。AI 能扩大执行能力，却没有取消这种判断。

## 方向选择

### 方案一：忠实深改（采用）

保留原有章节与时间线，让每个项目都推动一次认识变化。优点是作者提供的技术细节、个人判断和离职情绪都能留下；代价是文章会保持较长篇幅，需要严格删除口述重复。

### 方案二：压缩型回忆录

只保留三个代表项目和转正、离开两个节点。优点是阅读节奏快；代价是 OLAP、指标口径、Agent 稳定性、协作拆分等重要经验会被合并或删除，不符合用户要求。

### 方案三：主题型职业随笔

以“AI 时代研发还剩下什么”为主问题，云图经历只作为论据。优点是主题集中；代价是会改变现有故事线，也会让《云图回忆录》名不副实，不采用。

## 不可更改的事实

- 进入云图的第一天是 1024 程序员节；当天与朋友组队参赛并夺冠，之后办理入职。
- 在云图实习两年、正式工作两年，共四年。
- 离开云图后去字节 Seed 的 Infra 团队。
- 实习初期学习 Spark、Hive、HDFS、MapReduce 和后端开发。
- 第一个工作是把一个循环拉取、循环执行的老服务迁移为触发式入口；服务承载大量业务逻辑。
- 做过商品竞争分析，用人群流入、流出与竞争人群计算竞争关系；由此看到商家主观竞品与真实竞争商品可能不一致。
- 指标案例中，局部上更合理的 3500 万与平台既有口径 3350 万发生冲突；最终判断是一致性在该产品情境下比局部准确性更重要。
- 做过从 Hive 聚合结果、ClickHouse 查询链路转向 Bitmap 查询时聚合的 OLAP 方案，并看见灵活性背后的 CPU、内存、SSD、稳定性和成本问题。
- 转正答辩首轮表现不理想，随后争取加面并拿到很好的 offer；秋招还拿到阿里、腾讯、Kimi 等 offer，最终选择留在字节。
- 正式入职后做过实体切词与 Multi-Agent 项目；实体切词存在“老虎作为动物不能切、作为达人可以切”的业务例外。
- 业余搭过 Agent 平台、体验大模型服务并写成文档；这份积累后来带来承接组内 Agent 项目的机会。
- 大型 Agent 项目涉及多角色协作；作者负责拆分组件、组织上下文和责任边界。
- 目前代码几乎全部由 AI 生成，这是作者个人工作方式的陈述，不外推为所有研发的现状。
- 离开前又在一次 AI Agent 比赛中夺冠；文章首尾各有一个 1024 冠军。

## 必须保留的判断与表达

以下内容保留其含义，必要时修正口述病句，但不为了缩短文章而删去：

- “so fresh”作为进入云图和再次出发时的个人感受。
- 老服务再乱，只要肯花时间把调用和分支理清，仍然可以被改动。
- 互联网行业里重要的特质是细致和靠谱；聪明不能替代把事情接住。
- 数据提供了比主观位置更客观的视角，但数据口径仍然服务于真实的产品决策。
- 一致性有时比局部准确性更重要；客户一旦 confused，解释会非常昂贵。
- 功能收益、资源成本与稳定性需要一起计算 ROI；“漂亮”不等于值得做。
- “人生要么 suffering，要么 boring”，职业早期比起 boring，更愿意承受有价值的 suffering。
- 程序员是在“焦油坑”里持续挣扎的职业；业务例外不能靠拒绝业务消失。
- Agent 的灵活性与生产稳定性存在真实张力；探索环节可以开放，确定性交付环节需要明确控制。
- Connect the dots：当时不知道有什么用的积累，会在未来的机会里重新连接。
- 项目变大以后，主要麻烦经常来自人；组件拆分也在拆沟通线、上下文和责任。
- 一个问题只有带着足够上下文，才真正成为可以讨论的议题。
- AI 时代研发仍然需要靠谱、定义问题和设计品味；保留 “Taste is all you need”。
- 人并不总是冲浪者，有时只是被浪推着走；要对个人能力与时代红利保持清醒。
- 保持强观点，同时保持足够小的 ego，愿意被证据和他人的反驳说服。
- 不只以“研发”定义自己，而以 Builder 的心态从头到尾对用户问题负责。
- 技术变化很快，但分布式系统的基本判断和持续学习能力会迁移；“一法通万法”。
- 云图很好，但作者希望补完整能力拼图，从业务问题走向更底层的 Infra。

## 叙事运动

### 开头：第一个 1024

以比赛结束后办理入职的动作开场。只写当时觉得一切都很新，不提前总结四年意义。随后交代四年跨度和即将去 Seed Infra 的写作契机。

### 实习：从把功能做完到计算系统代价

老服务迁移负责建立“肯花时间就能理清复杂系统”的第一层信心；商品竞争分析把认识推进到数据的价值与口径一致性；OLAP 项目再反过来限制“更灵活一定更好”的直觉。三段不是项目罗列，而是同一个工程判断逐步变复杂。

### 转正：被看见、被校正与主动选择

技术分享和文档说明积累如何被看见；答辩失利保留“无知的顶峰”带来的校正；加面与 offer 不写成履历展示，而是解释为何作者最终选择“和优秀的人做有挑战的事”。

### 正式工作：业务混沌与生产中的 Agent

实体切词呈现业务例外的混沌；Multi-Agent 项目把同一个问题放大到灵活性、稳定性和业务主张之间的取舍。随后由个人业余积累进入 connect the dots，再进入大型项目中的协作、组件拆分和上下文管理。

### AI 时代：研发能力被重新暴露

不另起一套脱离前文的宏大宣言。每个判断都回扣已经出现的项目：靠谱来自老服务，品味与 ROI 来自 OLAP，定义问题来自 Agent，Builder 来自跨角色协作。明确这些是作者在当前阶段的判断，不写成所有组织都适用的定律。

### 离开：第二个 1024

感谢相信和给机会的人，也承认组织回报是作者在自身经历中的观察。把 Spark、OLAP 与新 Infra 工作连接起来，说明技术名词会变、基本问题仍在。最后写第二次 1024 冠军与新的 “so fresh”；回环提供新的含义，不重复开头的总结。

## 语言与编辑约束

- 保留英文术语，但统一大小写与必要空格；能用自然中文说清的口述连接词改为中文。
- 删除“然后呢”“其实”“这个事情”等无信息重复，不删除承载犹豫、判断边界或个人节奏的口语。
- 不虚构场景和对白，不夸大项目结果，不把个人经历外推成行业定律。
- 不把 offer、冠军和组织经历写成观点更可信的资格证明。
- 不把每个项目都收束成一句整齐金句；原稿中的重要判断自然落在事实之后。
- 二级标题沿用原稿的阶段结构，可以调整标题文字但不改顺序。
- 不机械压缩篇幅。删重复，保留完整因果、技术 trade-off 和关键个人判断。
- “Zed”统一为“Seed”；“异构”按上下文修正为 “ego”。

- AI 时代一节能从前文经验自然长出，不像独立拼接的观点文章。
